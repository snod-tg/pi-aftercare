# 真实模型 API 联调

日期：2026-10-18。推理服务由用户独立运行，Agent 只通过 HTTP 访问。

## 连接配置

在项目目录创建本地配置 `cp -n .env.example .env`。本次使用：

```dotenv
MODEL_BASE_URL=http://127.0.0.1:8080/v1
MODEL_NAME=aftercare-local
MODEL_API_KEY=local
MODEL_CONTEXT_WINDOW=8192
MODEL_MAX_OUTPUT_TOKENS=1024
```

`.env` 不提交 Git。`MODEL_BASE_URL` 以 `/v1` 结尾，Pi SDK 自动追加 `/chat/completions`。本次服务未启用 API Key 验证，`local` 是占位值。

`GET /health` 返回 `{"status":"ok"}`；`GET /v1/models` 返回别名 `aftercare-local`、约 8.95B 参数和 Q5_K Medium 量化信息，说明本次实际联调的是 9B，不能作为 4B 测试结果。

## 普通 API 请求

```bash
curl --fail http://127.0.0.1:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"aftercare-local","messages":[{"role":"user","content":"请用一句中文介绍自己。"}],"max_tokens":128,"stream":false}'
```

结果：`finish_reason=stop`，正式 `content` 非空，`reasoning_content` 未产生内容。输出 30 Token；服务报告输入处理 234.845 ms、生成 1904.025 ms，合计约 2.14 秒，生成速度 15.23 Token/s。这是单条短请求，不能外推为复杂 Agent 任务的整体延迟。

## 实际 Agent 闭环

运行 `./scripts/npm run chat`，输入：

```text
订单 O-1001，T恤换L码，外套退掉。请先给我方案，等待我确认。
```

首轮实际轨迹：`get_order` → `list_variants` 和 `get_aftercare_policy` → `quote_aftercare`。模型请求 4 次，工具执行 4 次。业务层生成 T 恤换 L 码、外套退货方案，退款 19900 分，等待确认。

终端输入实际输出的 `/confirm <方案ID>` 后：`get_request_status` → `create_aftercare_request`。模型请求 3 次，工具执行 2 次。业务回执显示申请已创建、`status=awaiting_return`、`refundStatus=not_started`。

本次只操作内存模拟订单，未处理真实资金。退出 Agent 后数据重置；推理服务继续运行。

## 发现与调整

首轮回复较冗长，中间解释曾把 99 元写成 99 分；最终报价与业务金额为正确的 199 元。模型还提示用户回复普通“确认”文字，但应用真正接受的确认入口是 `/confirm <方案ID>`，普通文字不能生成确认凭据。

据此在提示中明确金额换算、简短回复、直接调用工具和终端确认命令。提示约束不能替代业务层金额计算和授权校验。本次单例成功不能代表所有场景可靠，仍需多场景评测。

调整后重新启动 Agent、使用相同需求复测：模型直接调用工具，4 次模型请求、5 次工具执行后给出简短方案，金额为 199.00 元，并准确输出实际方案的 `/confirm` 命令。额外的一次尺码查询未改变业务结果。类型检查、31 项自动化测试、SDK/HTTP 检查及编译均通过。

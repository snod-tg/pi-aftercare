## 逐例诊断

### 9B / 9B，第0项：读到正确数据，却选错商品

原始需求是Google Home兼容的恒温器。get_product_details实际返回Google Assistant、黑色、可售的7747408585。Agent却说没有兼容款，引导客户改选Alexa，最后将4953074738写入申请；这不是工具没查到数据。

客户模拟器还编造了任务未提供的邮箱，第一次身份查询失败；后续又接受了偏离原目标的Alexa替代品。双方的错误叠加，最终申请存在，但业务状态不符合原任务，得0分。

证据：`.data/evals/tau-full-2026-10-19-9b-32k/runs/retail-0000-01.json`，商品查询返回值、用户后续确认及exchange_delivered_order_items参数可相互核对。

### 9B / 9B，第1项：客户提前停止，申请没有提交

Agent已查到Google Assistant款，并在解释退款后请求用户确认。客户模拟器此时直接输出结束标记，未确认也未触发换货写入，最终0分。

Agent也曾向身份查询工具传空邮编；客户提供了另一个编造邮箱，造成额外查询。该轨迹不能全部归因于Agent不会换货，也不能视作用户模拟器合格。

证据：同目录`retail-0001-01.json`，末尾是确认问题与用户结束标记，工具轨迹没有exchange_delivered_order_items。

### 9B / 9B，第2项：部分回答正确，完整任务失败

任务既要求查询T恤选项数量，也要求退三件商品。Agent给出了在售10项，评分中的r_outputs=1；但客户模拟器声称不知道任务已提供的邮编，身份确认和退货未完成。

官方总奖励还检查最终数据状态，不只检查文字答案；按该评分实现可推断，文字条件满足而状态未匹配，因此总分仍为0。该任务的reward_info只保留输出检查详情，不能将r_outputs=1误读成整项成功。

证据：同目录`retail-0002-01.json`；固定版本官方`tau_bench/envs/base.py`的calculate_reward先比数据状态，再检查输出。

### 9B / 4B，第0项：没有收集完整需求就执行不可重复的变更

客户先说键盘，Agent确认后立即提交键盘换货。客户随后才说恒温器，Agent第二次提交被工具拒绝，因为订单已从delivered变成exchange requested。最后转人工，仍未达到原始目标。

官方规则明确要求：换货工具只能调用一次，执行前收集全部换货商品，并提醒客户确认已提供所有商品。Agent缺少这一步；客户任务要求一次办完，却先确认了局部操作，后面又称自己一开始就完整说明了需求，轨迹不支持这句话。

证据：`.data/evals/tau-full-2026-10-19-agent9b-user4b-32k/runs/retail-0000-01.json`；第二次换货工具返回non-delivered order cannot be exchanged。

## 耗时与模型大小

在同一个第0项上，9B/9B为297.3秒、13次模型请求；9B/4B为434.7秒、15次模型请求，耗时增加约46.2%。后一次增加了失败的第二次换货、状态查询和转人工，因此不能推断4B推理本身更慢。

任务总延迟取决于输入处理、生成长度、模型轮数和工具执行。当前评测逐项运行，同一任务内双方交替请求；4个模型服务槽位主要是容量余量，不会自动将顺序对话加速4倍。单4B尚无完整结果，暂不比较其成功率或平均任务耗时。

## done与reward的含义

| 字段 | 含义 |
| --- | --- |
| done=False | 整项对话尚未终止，不表示当前工具失败 |
| done=True | 已终止，仍需看最终reward是否为1 |
| 中间reward=0.0 | 官方环境尚未做终局评分，通常正常 |
| task_end reward=0.0 | 整项未通过 |
| status=completed | 执行循环正常结束，不等于业务任务成功 |
| 工具返回Error | 此次工具执行失败，可由后续步骤恢复 |
| status=error/timeout | 运行错误或预算/超时问题，需要结合错误字段分析 |

即使换货写入已成功，环境仍可能返回done=False，因为还要回复客户并等待用户结束对话。

## 能得出的结论与后续方向

1. 当前可见问题集中在需求收集、商品属性阅读、执行顺序和客户模拟器的指令遵循，未发现这些已结束样本由接口断连或超时造成。
2. 应单独审计客户是否编造信息、遗忘已知信息、接受错误目标或提前终止；客户模拟器不是可信的正确性裁判。
3. Agent执行不可重复的变更前，应确认完整商品清单；这条约束已有官方规则，需要检验模型是否实际遵守。
4. 后续对照需固定任务、规则、步数、采样配置和用户模拟策略，并重复运行；当前样本不足以判断模型大小或部署方式的整体优劣。

这些τ-bench结果使用Pi SDK、官方原生工具和官方政策。此路径没有调用Pi Aftercare的PostgreSQL业务后端、BM25检索或7个业务工具，因此不能据此断定项目的数据库事务或检索实现有缺陷。

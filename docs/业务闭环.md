# 第一阶段：可执行的售后业务模拟

## 演示目标

“上周买的 T 恤换大一码，外套退掉。”

Alice 的订单 `O-1001` 包含 T 恤 M 码（实付 9900 分）和外套 M 码（实付 19900 分）。T 恤 L 码有 2 件库存，XL 码无库存。后端给出换 L 码、外套退货的方案，退款金额 19900 分。所有金额使用整数分。

运行 `./scripts/npm run demo`，无需启动独立服务或配置模型密钥。演示通过 Fastify 的注入接口调用真实路由，显式模拟客户确认和响应丢失后的重试；它不是模型自主完成任务的评测。

## 状态与执行

1. 查询当前身份拥有的订单和对应政策。
2. 报价检查签收时间、数量、商品和库存；记录订单、政策及目标库存的版本，有效期 10 分钟。不扣库存、不生成申请。
3. 客户通过独立确认接口确认指定方案。确认记录绑定客户、商家与不可修改的方案 ID。
4. 提交时再次校验有效期、确认归属、订单及库存版本；任何变化都要求重新报价和确认。
5. 所有校验通过后，单次同步操作更新订单已申请数量、预留替换库存、创建申请并记录幂等结果。
6. 申请状态为 `awaiting_return`，退款状态为 `not_started`；后续商品验收和真实退款未实现。

同一个方案不能用不同操作键重复提交。同键同参数返回原申请，同键不同参数返回冲突。必须先检查已有幂等结果再校验方案有效期，否则已成功但丢失响应的请求会在重试时因过期而被错误拒绝。

内存模型的同步方法在单个 Node.js 进程内没有异步切换点。它用于验证业务规则，不等于数据库事务、数据库唯一约束或跨进程锁。重启后记录重置，持久化和崩溃恢复将在后续实现。

## HTTP 接口

除 `/health` 外，接口使用演示令牌。Alice：`Authorization: Bearer demo-alice`；Bob：`Authorization: Bearer demo-bob`。这些公开的本地演示令牌不能用于生产登录。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/health` | 健康状态 |
| GET | `/orders/:orderId` | 查询当前客户订单 |
| GET | `/orders/:orderId/policy` | 获取模拟政策、版本和条款 |
| GET | `/orders/:orderId/lines/:lineId/variants` | 查询同款尺码与库存 |
| POST | `/quotes` | 生成方案 |
| POST | `/quotes/:quoteId/confirm` | 客户确认指定方案 |
| POST | `/requests` | 按已确认方案创建申请，支持幂等重试 |
| GET | `/requests/:requestId` | 查询申请 |
| GET | `/operations/:idempotencyKey` | 查询当前客户的业务操作是否完成 |

报价输入：

```json
{
  "orderId": "O-1001",
  "actions": [
    { "kind": "exchange", "lineId": "LINE-TEE", "quantity": 1, "targetVariantId": "SKU-TEE-L" },
    { "kind": "return", "lineId": "LINE-JACKET", "quantity": 1 }
  ]
}
```

确认输入必须为 `{ "confirmed": true }`。创建申请输入是服务返回的 `quoteId`、`confirmationId` 和由调用端为该业务操作保留的 `idempotencyKey`。退款金额、客户身份和库存数量不能由请求覆盖。

`/operations` 的 `completed` 只表示创建申请操作已完成，不代表退款完成。`not_found` 表示当前内存记录中没有该客户的操作结果，不能据此推断外部支付系统的状态。

错误结构：`{ "error": { "code": "QUOTE_STALE", "message": "..." } }`。无身份返回 401；无资源或资源不属于客户统一返回 404；方案失效、库存和幂等冲突返回 409；非法参数返回 400。

## Pi 工具

| 工具 | 用途 |
|---|---|
| `get_order` | 查询当前绑定身份的订单 |
| `get_aftercare_policy` | 获取结构化模拟政策 |
| `list_variants` | 查询同款尺码 |
| `quote_aftercare` | 创建待确认方案 |
| `create_aftercare_request` | 按用户确认提交方案 |
| `get_request_status` | 按原幂等键恢复查询结果 |

身份由宿主绑定在工具闭包中，模型参数不包含客户 ID。会话只启用这些工具，不加载个人 Pi 扩展、技能或通用编码工具。

没有 `confirm_quote` 工具：HTTP 确认接口与命令行 `/confirm` 都是单独的宿主操作，模型无权调用。工具注解只是提示，后端与会话宿主仍校验确认记录；不能把自然语言中的泛泛同意直接当作任意新方案的确认。

SDK 离线检查验证会话创建及上述工具注册；模拟 API 的集成测试进一步验证多轮执行、确认和运行上限。真实模型的工具选择与自然语言交互仍待联调。

## 已验证的关键场景

- 多商品换货加部分退货，按实付金额报价。
- 未确认或使用另一份方案的确认记录时不能提交。
- 不可访问他人订单、方案和申请；操作查询按客户隔离。
- 非法数量、重复商品行、跨款换货、原 SKU 换原 SKU、无库存均被拒绝。
- 订单状态、退换货期限、政策更新和方案过期影响业务资格。
- 确认后库存变化时要求重新报价，不产生部分操作。
- 响应丢失后查询、重复提交、过期后的已完成操作重放。
- 同键不同参数、同方案换键提交均不会创建第二份申请。
- 最后一件库存的竞争只成功一次；此处验证范围是单进程模拟器。
- HTTP 拒绝额外金额/身份字段、字符串数量、格式损坏的 JSON。
- Pi 工具返回可辨识的业务错误码，不把工具失败包装成成功文本。

本阶段包含 19 个业务/接口/工具测试；加上模型配置和多轮对话集成测试，目前共 31 个测试用例。测试数不等于独立业务评测样本数或 Agent 成功率。

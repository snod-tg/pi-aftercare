## 当前独立服务

服务器本机 API：`http://127.0.0.1:8000/v1`，模型别名 `aftercare-4b`。仅监听服务器回环地址；从 Mac 使用时需要 SSH 转发，不能直接将 Mac 的 `127.0.0.1:8000` 当作服务器地址。

服务目录：`/home/user/workspace/pi-aftercare-model/`。其中 `vllm-4b.pid`、`vllm-4b.log`、`4b-server-command.json` 保存当前进程、日志和启动参数。模型服务没有加入 Agent 应用的生命周期管理。

以下是本次启动参数记录，现有服务已在运行，不要重复执行：

```bash
/home/user/.venv/bin/vllm serve /home/user/Models/Qwen3.5-4B \
  --host 127.0.0.1 --port 8000 --served-model-name aftercare-4b \
  --dtype bfloat16 --language-model-only \
  --max-model-len 32768 --max-num-seqs 4 \
  --max-num-batched-tokens 4096 --gpu-memory-utilization 0.90 \
  --enable-prefix-caching --generation-config vllm \
  --enable-auto-tool-choice --tool-call-parser qwen3_coder \
  --reasoning-parser qwen3 \
  --default-chat-template-kwargs '{"enable_thinking":false}'
```

服务使用现有本地权重，启动环境设置了 `HF_HUB_OFFLINE=1` 和 `TRANSFORMERS_OFFLINE=1`。首次启动完成了编译、预热和 CUDA Graph 捕获。日志显示 KV cache 可容纳约 344,301 token；调度并发仍限制为 4，每个请求输入与输出合计最多 32,768 token。

## 基础测速

原始记录：[测速 JSON](experiments/vllm-4b-4090d-2026-10-19.json)。服务器本机 HTTP 流式请求，模型已预热；每次使用不同前缀，样本的 prompt cache 命中均为 0。不包含 Mac 至服务器的网络耗时。

为稳定比较吞吐，合成测速用 `ignore_eos=true` 固定输出 token 数；这不是业务任务成功率。首输出时间是客户端接收到第一段可见输出的时间；“输出阶段速度”按首段至末段输出计算，在并发场景中也包含其他请求预填充对本请求的影响。

| 场景 | 每路输出 | 首输出时间中位数 | 每路输出阶段速度中位数 | 每路总耗时中位数 |
| --- | ---: | ---: | ---: | ---: |
| 单路短输入（约62 token） | 256 token | 0.047秒 | 101.67 token/s | 2.55秒 |
| 单路约8K输入 | 256 token | 0.57秒 | 98.63 token/s | 3.15秒 |
| 单路约31K输入 | 256 token | 2.50秒 | 91.53 token/s | 5.29秒 |
| 四路短输入同时请求 | 每路256 token | 0.083秒 | 89.20 token/s | 2.94秒 |
| 四路约31K输入同时请求 | 每路64 token | 6.56秒 | 16.54 token/s | 10.75秒 |

四路短输入总输出吞吐约 347.38 token/s。四路长输入测试成功，但预填充竞争明显，不能将短输入的速度直接套用到长输入。测试完成后 GPU 显存约 21.3GiB（包括预分配缓存），健康接口返回 200。

普通聊天返回有效正文且没有 reasoning 输出；`tool_choice=auto` 返回了标准 `tool_calls`，函数 `get_order` 和参数 `{"orderId":"O-1001"}` 校验通过。

## 同时跑几项任务

用户在本次测速后明确改为希望多项任务并行，不再沿用之前的逐项评测要求。建议下一轮全量评测采用 **4 个独立任务 worker**，共用同一模型 API；模型端 `max_num_seqs=4`、每请求 32K 不变，各任务拥有独立 Agent 和用户模拟器上下文。单个任务中的两者交替调用，不应简单理解为每个任务必然同时占用两路推理。

补测使用相同输入规模、相同输出量，对比 1/2/4 请求同时进入 API；每组重复两次。原始数据：[并发对比 JSON](experiments/vllm-4b-concurrency-2026-10-19.json)。

| 输入与每路输出 | 并发请求 | 总输出吞吐（包含预填充） | 每路总耗时中位数 |
| --- | ---: | ---: | ---: |
| 约8K输入，128 token输出 | 1 | 68.36 token/s | 1.87秒 |
| 约8K输入，128 token输出 | 2 | 99.07 token/s | 2.56秒 |
| 约8K输入，128 token输出 | 4 | 135.60 token/s | 3.72秒 |
| 约31K输入，64 token输出 | 1 | 20.07 token/s | 3.18秒 |
| 约31K输入，64 token输出 | 2 | 21.97 token/s | 5.75秒 |
| 约31K输入，64 token输出 | 4 | 23.28 token/s | 10.79秒 |

在约8K输入这组中，四并发比两并发总吞吐提高约37%，比单请求提高约98%；约31K输入时，四并发比两并发仅高约6%。所以，以尽快完成离线评测为目标，四项并行是已测配置中的首选；如果实际任务多数接近32K，额外收益有限，后续应依据真实任务吞吐和超时情况再调整。这里是 API 工作负载对比，不是完整 τ-bench 任务吞吐的实测，不能据此承诺全量完成时间减半。

现有全量脚本仍是逐项调度，尚未修改或重新启动。实际启用四项评测还需要添加任务并发调度，不能只修改模型服务的并发参数。新服务器使用 BF16，与旧的本机量化模型有差异，下一轮应使用新的运行目录和配置记录，不能混入本地已完成的15项结果。

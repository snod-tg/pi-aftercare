- 整轮约1800.3秒，约5.50项/分钟；单任务时长中位数39.60秒，P90约73.30秒。
- 任务时长总和7133.75秒，除以墙钟时间约3.96，说明任务调度总体维持了四项重叠；不能称为相对单并发实测提速3.96倍，因为没有同配置单并发全量对照。
- SDK记录的Agent累计token为20,000,840；顾客API累计total_tokens为2,506,882。包含多轮重复提示及各自缓存统计口径，不能当作单次上下文大小、实际唯一token或账单金额，也不能据此计算纯生成速度。

## 下一轮建议，按优先级

1. **先补观测，保留本轮基线。** 顾客异常记录finish_reason、可见正文长度、completion_tokens；Agent截断保存停止原因和可审计的部分输出。当前日志无法判断那1个顾客异常的具体原因。不要通过把所有error排除出分母来美化45.45%。
2. **先检查评测顾客的可靠性。** 对已确认的意图漂移、编造地址、遗漏数量和无法结束分别建立诊断案例；可用更强的独立顾客服务做对照，Agent固定4B，保持官方任务和规则不变。顾客模型变化必须单独记录，不能把成功率变化全部算成Agent优化收益。
3. **针对4个输出截断做预算对照。** 固定Agent/顾客模型、规则和32K窗口，仅把Agent输出从1024提高到2048，先观察截断是否消失及目标是否完成，再决定是否应用全量。不要假设消除截断就一定成功。
4. **改进多目标和业务对象核对。** 在自建售后链路维护明确的订单、商品规格、数量和未完成目标；写入前对照完整目标与确认内容。涉及重复item ID时保留数量。用真实工具结果核实事实和资格，不依赖模型一句“符合政策”。在原生τ评测中改变提示或策略也应标记为新的实验变体。
5. **处理收尾循环和双重预算。** 区分业务完成、用户终止、步数耗尽；记录模型调用和环境动作两种预算。不要用不断增加步数掩盖寒暄循环，也不要擅自将未终止任务判成功。对诊断案例可单独审计最终状态，但正式得分沿用原协议。

每次只改一个主要变量，保存新目录与配置；定向诊断通过后再复跑完整165项。如果新旧实验都只采样一次，逐项变化只能视为观察结果，需要重复试验才能判断改善是否稳定。自建售后工具的确认门禁、幂等、持久化和故障恢复仍需由项目自身测试单独证明。

## 复现统计

在项目目录运行，不调用模型，不修改原始成绩：

```bash
.venv/bin/python -m evals.analyze_tau \
  --run-dir .data/evals/tau-full-2026-10-19-vllm4b-c4-32k \
  --audit-unfinished
```

默认写入原运行目录的`analysis.json`。`--audit-unfinished`在全新上游内存数据中重放已记录工具，需要已安装的τ依赖；没有模型或真实业务数据库调用。报告的案例是人工核查，自动脚本负责覆盖率、分数、结果分类、耗时和离线重放。

# 故障注入与业务状态评测

`ToolFaultInjector` 只能由测试/评测代码显式传入，不提供给模型，不通过用户对话或工具参数启用。规则指定工具、调用次数（默认首次）、before/after 时机，以及 error、response_lost、delay 或 effect。每条触发记录包含时间和工具；不是模型指令。

- before error：工具尚未执行就失败，错误返回下一轮模型。
- after response_lost：业务操作已完成，但模拟工具响应丢失；不能把错误等同于写入未发生。
- delay：模拟慢工具；真正执行前再次经过会话状态/步数检查，取消或超时后不能开始新的写入。已经在执行的数据库事务仍可能提交，需查询原操作键恢复。
- effect：测试宿主可在确认后修改库存或政策；模型无权触发。
- PostgreSQL beforeCommit 钩子：在真实事务提交前抛错，验证订单、库存、申请、幂等记录一起回滚。

`tests/faults.test.ts` 使用模拟模型 HTTP/SSE，但运行实际 Pi SDK 和业务工具，验证一次性错误恢复、提交后丢响应、库存变化及慢写入在超时后的拦截。模型 HTTP 故障、循环上限、伪造确认等由 conversation 测试覆盖。

## 可执行评测

```bash
./scripts/npm run eval -- --mode fixture --trials 3
./scripts/npm run eval -- --mode live --case mixed --trials 1 --output .data/evals/live.json
./scripts/npm run eval -- --help
```

fixture 模式不连接模型，使用明确标识的脚本响应。live 模式通过配置的模型 API 完成自然语言与工具决策，不覆盖真实数据库数据：每次评测新建隔离的内存业务状态。两种模式都调用实际 Pi 和业务工具；评测用户只确认第一份有效方案，不会自动批准后续重报方案。

内置 8 类：混合退换、未确认、缺货、跨客户订单、读工具失败、提交响应丢失、确认后库存变更、模型接口错误。model_error 场景只用于 fixture 模式，避免把真实服务故障人为替换后当作模型测评。

评分检查最终申请、金额、商品操作、库存、已申请数量、终态及故障是否触发；不根据模型说“完成”给分。只检查这些定义好的状态投影，尚未评估所有语言表达、政策引用准确率或用户体验。

报告保存开始时间、耗时、模型/工具次数、服务返回的 Token、工具轨迹、故障记录、预期和实际状态。它是项目自建场景的评测，不是官方 τ-bench 成绩。生成的完整报告位于忽略 Git 的 `.data/evals/`，样例摘要在 `evals/reports/`。

`pass^k` 估计随机选 k 次都成功的概率：每个场景有 n 次运行、c 次成功时，使用 C(c,k)/C(n,k)。它与至少一次成功的 pass@k 不同；仅在 n≥k 时报告。fixture 的重复运行是确定性回归，不提供模型可靠性或统计显著性证据。费用未知时不按 0 元计价。

# PostgreSQL 持久化与事务

模型服务与数据库均独立运行。Agent 和 HTTP 服务在配置相同 `DATABASE_URL`、`DATABASE_SCHEMA` 时共享业务数据；没有 DATABASE_URL 时使用内存演示。

## 本机运行

已安装 PostgreSQL 17，默认程序目录 `/opt/homebrew/opt/postgresql@17/bin`。其他安装位置可设置 `PG_BIN`。从项目根目录执行：

```bash
./scripts/npm run db:local -- start
./scripts/npm run db:init
./scripts/npm run chat
```

专用数据库监听 `127.0.0.1:55432`，数据目录 `.data/postgres`，日志 `.data/postgres.log`。初始化时随机生成密码，保存在忽略 Git 的 `.data/postgres-password`，连接写入忽略 Git 的 `.env`；已有 DATABASE_URL 不会被覆盖。`PG_LOCAL_PORT` 可更改端口。没有注册开机自启，未启动 Homebrew 默认数据目录。

```bash
./scripts/npm run db:local -- status
./scripts/npm run db:local -- stop
./scripts/npm run test:postgres
```

停止后再次 start 不重置数据。db:init 可重复执行，不刷新签收日期、不补库存、不覆盖已有申请。备份应使用 PostgreSQL 原生备份工具；不要在运行时直接复制数据目录。

## 一致性设计

`migrations/001_aftercare.sql` 定义商家表和按种类分区的 JSONB 业务资源：政策、订单、SKU、方案、确认、申请、幂等操作。主键为 `(merchant_id, kind, id)`，申请的 quoteId 和确认的客户/quoteId 另有唯一索引，库存非负有 SQL CHECK。

写操作先 `BEGIN`，锁定商家行 `SELECT ... FOR UPDATE`，读取该商家的最新资源，调用同一套业务规则校验和计算，写入资源后提交。申请、库存、订单和幂等结果在同一个事务里；任一步失败全部回滚。只读操作使用 Repeatable Read 一致快照。事务只包含业务数据处理，不包含模型 HTTP 请求。

这是当前数据规模下的粗粒度锁方案：同一商家写操作串行，不同商家可以并行。每次会加载商家资源，不适用于大商家大订单量；扩展时需改成按订单和 SKU 锁行、分表和分页。它提供真实跨连接事务保证，不宣称已经具备生产吞吐能力。

相同操作键的结果持久化，提交成功但响应丢失时，查询 get_request_status 或复用原键可取回原申请。即使报价过期，已提交操作仍可幂等重放；相同键换参数会被拒绝。确认凭据和操作键也持久化，同一方案重复确认复用原凭据。

CLI 重启时恢复当前客户有效的最新待确认方案，可用 `/quotes` 查看，再执行 `/confirm <方案ID>`。CLI 本身不保存完整聊天历史。网页另有完整 PostgreSQL 会话持久化，包含 Pi 原始工具上下文、确认及消息，支持刷新和后端重启，见[网页说明](网页使用说明.md)。

## 验证

普通 check 离线运行，不要求数据库；真实测试必须显式运行 test:postgres，连接失败会使检查失败，不把跳过当成功。测试在随机独立 schema 中创建数据并清理，验证：

- 两个连接竞争最后一件库存：只有一个申请成功，库存为 0。
- 事务提交前注入失败：订单、库存、申请、幂等记录全部未变。
- 6 个并发重试返回同一申请；关闭重开连接后仍可恢复，跨过期时间仍可重放。
- 新 Agent 会话恢复待确认方案，并复用数据库中的确认和操作键。
